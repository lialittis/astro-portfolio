### [Package managers have an integrity problem](https://blog.trailofbits.com/2026/10/14/package-managers-have-an-integrity-problem/) - October 14, 2026

<p>I tested 25 of the most popular package managers to check whether they detect a compromised package repository injecting malicious code into legitimate packages. This code integrity problem could be solved using cryptographic hashes or signatures, but many package managers are still vulnerable to this threat. Of the 25 package managers reviewed<sup id="fnref:1"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:1">1</a></sup>, fewer than half used lockfiles that checked for tampering by default, and only two verified the integrity of every package they downloaded.</p>
<p>Supply-chain attacks caused by developer compromise are a common story, but imagine what happens if ongoing mitigation attempts, including work by Trail of Bits<sup id="fnref:2"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:2">2</a></sup>, are successful. If developers of popular packages are no longer the easiest targets, attackers will shift their focus to the next weakest link in the system: the package repositories that serve the code. The cryptographic answers to this problem are more subtle than they appear, and many implementations fall short due to deliberate design choices, resource prioritization, or the complexity of developer-friendly solutions.</p>
<p>One natural answer is to include a cryptographic hash of a package’s contents in a lockfile and compare hashes after downloading the package. This automatic verification was the default behavior in about half of the package managers I tested, but others required extra configuration to include or verify these hashes, used hashes in a cryptographically insecure way, or lacked hashes entirely. This is summarized in the following table.</p>

<p>As both tables show, I found a surprising variation in the cryptographic designs and the level of protection they provide. Despite the challenges, I also found several communities on the frontier of this integrity problem that are bringing improved designs to reality. This post explores those variations, showing where certain designs fall short, why code integrity is harder to solve than it appears, and what cryptographic designs might be adopted in the future.</p>
<h2 id="simulating-malicious-package-repositories">Simulating malicious package repositories</h2>
<p>Studying the cryptographic behavior of 25 package managers is quite the challenge. I wanted to minimize manual analysis, but also be 100% confident when I claim an attack from a malicious package repository is possible. To solve this problem, I built a testing harness based on Docker containers and <a href="https://www.mitmproxy.org/">mitmproxy</a> that dynamically evaluates the security of package managers against a malicious server.</p>
<p>

 <figcaption>Figure 1: Experimental design of the test harness used to simulate malicious package repositories</figcaption>
 </figure>
</p>
<p>The Ubuntu-based Docker images include a package manager, sample code, and optionally a lockfile. There are <a href="https://arxiv.org/abs/2505.04834v3">conflicting opinions</a> about whether to include lockfiles in source code repositories, so I tested both configurations. The harness instructs the package manager to fetch dependencies from the repository, and the resulting network request <a href="https://docs.mitmproxy.org/stable/concepts/modes/#wireguard">routes</a> through a WireGuard network to a custom mitmproxy addon.</p>
<p>Because the mitmproxy TLS CA is installed in the Docker image, the addon can fully manipulate the plaintext from the package repository, simulating a compromised server. I assumed any web-facing server could be compromised (e.g., Composer fetches metadata from Packagist and packages from GitHub), but backend resources, like any private signing keys, remain secure. The simulated repository embeds malicious code into the downloaded packages, and if the sample code executes the malware, the attack is successful.</p>
<p>I tried to keep the experimental setup reflective of real-world usage, but there are limitations. I installed the latest package manager versions, followed quickstart guides for setting up sample projects inside the container, and picked popular packages from public repositories to infect. I ran package manager commands with default flags to see if extra steps, like modifying the project manifest or running extra commands, were needed to enforce cryptographic integrity. However, I am limited to testing a single package with a single package manager version on a single platform, and the test conditions (e.g., PowerShell and CocoaPods on Ubuntu) may not represent the most common usage patterns. The setup isn’t meant to show that every developer is vulnerable to a malicious package repository, just that a developer following reasonable conventions is.</p>
<p>With the package managers installed and network intercept functional, one (mostly) promising observation is clear.</p>
<h3 id="https-is-almost-everywhere">HTTPS is (almost) everywhere</h3>
<p>Our harness architecture captures all network traffic, so it&rsquo;s easy to test that package managers are using TLS and validating the certificates. In almost every package manager, they are.</p>
<p>The exception is cpanminus, the <a href="https://www.cpan.org/modules/INSTALL.html">frequently</a> <a href="https://learn.perl.org/installing/unix_linux.html">recommended</a> package manager for Perl. cpanminus uses unencrypted HTTP by default to connect to the Perl package repository, allowing any active network attacker to inject malicious code into downloaded packages. This <a href="https://github.com/advisories/GHSA-9mmm-86g7-vp9g">vulnerability</a> has been known for years, but the cpanminus developer has not switched to HTTPS, since doing so would be a <a href="https://github.com/miyagawa/cpanminus/issues/611#issuecomment-648642186">breaking change</a> to default behavior.<sup id="fnref:3"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:3">3</a></sup></p>
<h2 id="hash-functions-dont-always-provide-integrity">Hash functions don&rsquo;t always provide integrity</h2>
<p>By using the mitmproxy addon to modify the package repository responses, I could investigate how different package managers use cryptographic hashes. Hashes are a natural way to ensure that a downloaded file has not been tampered with, but the main question is how the package manager learns the correct hash in the first place.</p>
<p>Microsoft&rsquo;s <a href="https://vcpkg.io/en/">vcpkg</a> package manager for C and C++ libraries offers an interesting example. The package manager source code includes content <a href="https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/zlib/portfile.cmake#L6">hashes</a> for <a href="https://github.com/microsoft/vcpkg/tree/master/ports">thousands</a> of dependencies. When a developer updates their library and wants to register the new content in vcpkg, they <a href="https://learn.microsoft.com/en-us/vcpkg/get_started/get-started-packaging">recompute</a> the hash of their package and open a <a href="https://learn.microsoft.com/en-us/vcpkg/get_started/get-started-adding-to-registry">pull request</a> against the vcpkg source code with the new hash and link to the package. When a package is downloaded by vcpkg, the hash is checked. So as long as the package manager is trusted, this approach is fully secure against a malicious package repository.<sup id="fnref:4"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:4">4</a></sup></p>
<h3 id="hashes-in-lockfiles">Hashes in lockfiles</h3>
<p>It is significantly more common that the package manager learns the correct hash via a lockfile. A lockfile is frequently created by a package manager, resides alongside a project&rsquo;s source code, and references specific versions of dependencies needed by the project. If a developer checks a lockfile with cryptographic hashes into the source code repository, and the user’s package manager validates downloaded packages against the hashes, then the user&rsquo;s dependencies perfectly match the developer’s.</p>
<p>This is how it works for the Bun package manager for JavaScript projects. Installing a package with <code>bun add</code> <a href="https://bun.com/docs/pm/cli/add">updates</a> the <code>bun.lock</code> lockfile; committing the lockfile to <a href="https://bun.com/docs/pm/lockfile#should-it-be-committed-to-git">Git</a> and calling <code>bun install</code> on another copy of the repo <a href="https://github.com/oven-sh/bun/blob/34cbb9a40b4bd1bd767d134a7065e66c2432a676/src/install/extract_tarball.rs#L47">verifies</a> the hash in the lockfile against the new copy of the dependency. Similar behavior is found in npm, pnpm, and Yarn (also JavaScript package managers); uv and Poetry (Python package managers); Bundler (for Ruby); Cargo (for Rust); and SwiftPM (for Swift).</p>
<p>Other package managers support lockfiles, but with more steps than the standard add/restore process. Python&rsquo;s Pip has <a href="https://pip.pypa.io/en/stable/cli/pip_lock/">experimental</a> support for the <code>pylock.toml</code> format, and Conda has the optional library <a href="https://conda.github.io/conda-lock/">Conda lock</a>. NuGet, the .NET package manager, generates a lockfile after <a href="https://devblogs.microsoft.com/dotnet/enable-repeatable-package-restores-using-a-lock-file/">adding</a> the <code>RestorePackagesWithLockFile</code> property to the project.</p>
<p>Many package managers (Maven, R, PowerShellGet, PSResourceGet, and cpanminus) do not have dedicated lockfiles, and some have lockfiles (Gradle’s <code>gradle.lockfile</code><sup id="fnref:5"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:5">5</a></sup> and Gem’s <code>Gemfile.lock</code>) without hashes in them.</p>
<h3 id="hashes-present-but-not-for-integrity">Hashes present, but not for integrity</h3>

This is not necessarily reflective of a vulnerability, since the underlying behavior is clearly documented, but it shows how there are multiple valid opinions about how lockfiles should be structured and consumed. Nevertheless, a user who is accustomed to the behavior of one package manager may be surprised by that of another.</p>

<h3 id="lockfiles-have-many-roles-besides-supply-chain-integrity">Lockfiles have many roles besides supply-chain integrity</h3>
<p>The previous experimental results show that lockfile hashes often <em>can be</em> used to enforce package integrity, but this is not their sole or even original purpose. Alternatively, they can lock dependencies to a particular functionality, enable an easy way for application developers to share a consistent environment, or facilitate reproducible builds. Analyzing package manager lockfiles through the lens of supply-chain security is a recent interpretation that can be at odds with their original design. The recent change to pnpm’s <code>--frozen-lockfile</code> is one example.</p>
<p>Another example of this tension is the question of whether the lockfile should be committed to version control. Most modern guidance recommends committing the lockfile for applications, since the final build environment is fully controlled. The question is more complicated for libraries, since package managers often ignore libraries&rsquo; lockfiles to avoid locking to conflicting transitive dependencies. Committing the lockfile makes it easier to develop the library by sharing a consistent build environment with other developers, but excluding the lockfile makes it easier to catch conflicts with different dependency versions before they are found by users. Many package managers recommend committing the lockfile for libraries (e.g., <a href="https://docs.npmjs.com/cli/v12/configuring-npm/package-lock-json">npm</a>, <a href="https://pnpm.io/git">pnpm</a>, <a href="https://python-poetry.org/docs/basic-usage/">Poetry</a>, <a href="https://docs.astral.sh/uv/guides/projects/#uvlock">uv</a>, and <a href="https://classic.yarnpkg.com/blog/2016/11/24/lockfiles-for-all/">Yarn</a>), some recommend excluding it (e.g., <a href="https://guides.rubygems.org/faqs/#using-gemfiles-inside-gems">Bundler</a>), and some leave it up to the developer (e.g., <a href="https://blog.rust-lang.org/2023/08/29/committing-lockfiles/">Cargo</a>).</p>
<p>Many of these questions are explored in a recent <a href="https://arxiv.org/abs/2505.04834v3">study</a> by Gamage et al. The authors explore lockfile design decisions for seven package managers, analyze published projects, and perform semi-structured interviews with 15 developers. They find that the practice of committing a lockfile varies by which package manager is used, and categorize five benefits to using lockfiles, as perceived by the interview subjects: build determinism, integrity, transparency into indirect dependencies, debugging, and security scanning. Some of the developers also preferred to not use lockfiles, citing a preference for end users to resolve to the latest version of a dependency, which may have more bug fixes and vulnerability patches.</p>
<p>The diversity of package manager designs and views surrounding the purpose of lockfiles makes it difficult to prescribe a single recommendation. With regard to supply-chain integrity, it is common, but not universal, to view lockfiles as a source of integrity that should be committed with the source code. For package managers with lockfiles that do not provide cryptographic integrity, it is worth considering whether their users share that expectation. Even when lockfile hashes can provide cryptographic integrity, locking to specific package hashes means that users do not immediately receive subsequent updates or security fixes, since the newer package has a different hash. This leads to frequent lockfile bumping to distribute the latest hashes. Wanting immediate updates is a separate concern from wanting package integrity, but the current, common approach of using hashes in lockfiles is at odds with that goal. In conclusion, lockfile hashes are often, but not always, effective at providing cryptographic integrity, but do not work in every situation.</p>
<h2 id="signatures-are-common-verification-is-not">Signatures are common; verification is not</h2>
<p>Signatures are a natural way to address these shortcomings, but implementations frequently fall short. In theory, developers could sign every release with their own private key, and the package manager could check the signature of the package it downloads from the package repository. In fact, signatures are relatively common in different package ecosystems, but proper signature validation is surprisingly lacking. The reality of using signatures to provide code integrity is more nuanced than it seems, and package managers have different approaches to the problem.</p>
<p>Many package managers have no signatures available. Arguably, vcpkg does not need them, because all package hashes are distributed with the manager, but this leaves Cargo, CocoaPods, Composer, Conan, Conda, Pub, R, and SwiftPM<sup id="fnref:7"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:7">7</a></sup>. The Conan developers are aware and previously decided not to fix it, <a href="https://github.com/conan-io/conan/issues/1959">citing</a> several implementation challenges and suggesting organizations where integrity is critical could run their own repository server. Cargo developers are actively <a href="https://rustfoundation.org/media/improving-supply-chain-security-for-rust-through-artifact-signing/">considering</a> different signing designs, but this effort is still in progress. Composer developers have been <a href="https://blog.packagist.com/an-update-on-composer-packagist-supply-chain-security/">implementing</a> many new protections against supply-chain attacks, with future plans for artifact integrity.</p>
<h3 id="repository-signing">Repository signing</h3>
<p>One straightforward approach, known as repository signing, is when the package repository signs every package once it&rsquo;s uploaded, and the repository&rsquo;s public key is distributed with the package manager. This doesn&rsquo;t solve the problem of a totally compromised package repository, since a malicious package repository could legitimately sign a malicious package, but it would protect against untrusted mirrors or a partial compromise of a package repository&rsquo;s serving infrastructure.</p>
<p>Repository signatures are used by the <a href="https://docs.npmjs.com/about-registry-signatures">npm Registry</a>, the <a href="https://learn.microsoft.com/en-us/nuget/reference/signed-packages-reference">NuGet Registry</a>, and the PAUSE server for Perl module distribution. In the npm Registry, signatures are distributed within package <a href="https://registry.npmjs.org/debug">metadata</a> with repository-specific <a href="https://registry.npmjs.org/-/npm/v1/keys">public keys</a>. NuGet Registry repository signatures are found in <code>.signature.p7s</code> <a href="https://devblogs.microsoft.com/dotnet/introducing-repository-signatures/">files</a> within the distributed ZIP package, again with repository-specific <a href="https://api.nuget.org/v3-index/repository-signatures/5.0.0/index.json">public keys</a>. The PAUSE server takes a different approach, using its <a href="https://pause.perl.org/pause/query?ACTION=pause_04about#pubkeybat">GPG key</a> to batch sign the <a href="https://cpan.metacpan.org/authors/id/S/SR/SRI/CHECKSUMS">cryptographic hashes</a> of several packages at a time.</p>
<h3 id="developer-signing">Developer signing</h3>
<p>Developer signing involves the developer maintaining the private key and signing the package before uploading it to the repository for distribution. This prevents the package repository from tampering with the contents, but it also provides a way for the package repository to authenticate the uploader.</p>
<p>There are two common approaches for a developer asserting their public key. In the first approach, the public key is distributed out-of-band. The Maven Central repository (used by Maven and Gradle) and the RubyGems repository (used by the <code>gem</code> and Bundler package managers) <a href="https://docs.ruby-lang.org/en/master/Gem/Security.html">both</a> <a href="https://central.sonatype.org/publish/requirements/#sign-files-with-gpgpgp">support</a> this type of developer signing. Maven Central uses PGP signatures, and developer keys are distributed by <a href="https://central.sonatype.org/publish/requirements/gpg/#signing-a-file">public keyservers</a>. RubyGems uses self-signed certificates, and their distribution is left to the developers (e.g., <a href="https://github.com/rspec/rspec/blob/main/rspec/certs/rspec.pem">rspec</a>). The major difference is that developer signing is mandatory for Maven Central, and optional for RubyGems. Developer signing is rare for RubyGems, <a href="https://guides.rubygems.org/security/">due to</a> the lack of an established chain of trust, and a previous attempt to introduce a certificate authority <a href="https://www.grant-olson.net/news/2013/09/29/nobody-cares-about-signed-gems.html">failed</a>.</p>
<p>The second approach involves a chain of trust. The NuGet Registry and PowerShell Gallery both support developer signatures. Neither makes signatures mandatory, but the PowerShell Gallery <a href="https://learn.microsoft.com/en-us/powershell/gallery/concepts/publishing-guidelines?view=powershellget-3.x#sign-your-code">recommends</a> it and the NuGet Registry has strict <a href="https://learn.microsoft.com/en-us/nuget/reference/signed-packages-reference#signature-requirements-on-nugetorg">requirements</a> if developer signing is used. In both, the developer&rsquo;s key must chain to a <a href="https://learn.microsoft.com/en-us/nuget/create-packages/sign-a-package#get-a-code-signing-certificate">trusted CA</a>, and acquiring a valid code-signing certificate can <a href="https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options">cost</a> hundreds of dollars per year. The benefit of this approach is that trusted root certificates can be preinstalled on the platform, allowing package managers to verify public keys.</p>
<p>One downside of developer signing is that developers are responsible for key management, and they can lose the ability to update their code if they lose access to their key.</p>
<h3 id="identity-based-signing">Identity-based signing</h3>
<p>An increasingly common middle ground is &ldquo;identity-based&rdquo; or &ldquo;keyless&rdquo; signing from <a href="https://docs.sigstore.dev/cosign/signing/overview/">Sigstore</a>. Rather than require developers to manage long-term private keys, a developer can use Sigstore&rsquo;s Fulcio CA to issue a fresh signing certificate on demand, for free. To prevent impersonation, the developer proves their identity with an OIDC token: a cryptographically signed statement from a third party like Google, Microsoft, or GitHub that attests to the email address, username, or potentially other claims about the developer&rsquo;s identity. The verifier can check that the username is correct and the certificate chain links back to Sigstore Fulcio&rsquo;s root certificate, proving that someone with access to that account created the signature.</p>
<p>Keyless signing is particularly useful because it can be integrated into a developer&rsquo;s existing workflow-based deployment pipeline. This is frequently called <a href="https://blog.trailofbits.com/2024/11/14/attestations-a-new-generation-of-signatures-on-pypi/">provenance</a> attestation or trusted publishing<sup id="fnref:8"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:8">8</a></sup>. GitHub and GitLab provide OIDC tokens to Actions and CI/CD workflows that attest to the build workflow, the repository, and the commit hash. A workflow can use this token to obtain a signing certificate from Sigstore, sign the built package, and upload the signed package to the package repository. Since the signing certificate includes the commit hash and workflow details, this cryptographically links the built binary artifact to its source code.</p>
<p>Provenance attestation via Sigstore is supported by Python&rsquo;s <a href="https://blog.trailofbits.com/2024/11/14/attestations-a-new-generation-of-signatures-on-pypi/">PyPI</a>, the <a href="https://docs.npmjs.com/generating-provenance-statements">npm Registry</a>, <a href="https://blog.rubygems.org/2023/12/14/trusted-publishing.html">RubyGems repository</a>, and <a href="https://central.sonatype.org/news/20250128_sigstore_signature_validation_via_portal/">Maven Central</a>. While Sigstore attestations are not mandatory, there is already <a href="https://trailofbits.github.io/are-we-pep740-yet/">better</a> <a href="https://segiddins.github.io/are-we-attested-yet/">adoption</a> than RubyGems’ optional support for developer-managed signing keys.</p>
<h3 id="verification-code-is-skipped-unconfigured-or-nonexistent">Verification code is skipped, unconfigured, or nonexistent</h3>
<p>Unfortunately, just because these signatures exist does not mean they are being verified by package managers.</p>
<p>In the npm package manager, the repository signatures are not checked when running <code>npm install</code>. Checking the signatures requires running <code>npm audit signatures</code>, which uses Sigstore to validate the <a href="https://github.com/sigstore/root-signing/blob/main/targets/registry.npmjs.org/keys.json">registry public keys</a> and then validates the signatures of the installed packages. pnpm recently added the <code>pnpm audit signatures</code> <a href="https://pnpm.io/cli/audit#signatures">command</a>, but that implementation fetches the registry public keys from the potentially malicious registry rather than verifying with Sigstore, so an adversary could simply add their own key and signature. Bun and <a href="https://github.com/yarnpkg/berry/issues/6487">Yarn</a> currently lack an equivalent <code>audit signatures</code> command.</p>
<p>In the NuGet package manager, the <a href="https://learn.microsoft.com/en-us/nuget/reference/nuget-config-file">default</a> <code>signatureValidationMode</code> is <code>accept</code>, which installs invalidly signed packages. The user must set this to <code>require</code> and configure the list of trusted signers, such as with <code>dotnet nuget trust source</code>. These configurations (which include the repository public keys) can be securely distributed within a <code>nuget.config</code> configuration file, functioning as a lockfile that locks the trusted signers.</p>
<p>Ruby&rsquo;s Gem and Bundler, and Java&rsquo;s Maven and Gradle, which all use repositories with developer signatures, do not verify signatures by default. They require the user to manually add developer public keys (<code>gem cert --add</code>) or list the allowed public keys that should be trusted. In Maven, one can use the third-party <code>pgpverify-maven-plugin</code> with <code>pgp-keys-map.list</code> to specify the trusted PGP fingerprints. Gradle offers <a href="https://docs.gradle.org/current/userguide/dependency_verification.html">dependency verification</a>, which works similarly.</p>
<p>Finally, several package managers seemingly lack any sort of verification code at all. <a href="https://github.com/pypa/pip/issues/12766">Pip</a>, <a href="https://github.com/astral-sh/uv/issues/9122">uv</a>, and Poetry do not currently have a way to verify identity-based attestations described in PEP740. cpanminus <a href="https://metacpan.org/dist/App-cpanminus/view/bin/cpanm">does not</a> have a way to verify the integrity of the repository-signed CHECKSUMS file. It once did, but in response to a verification bypass <a href="https://blog.hackeriet.no/cpan-signature-verification-vulnerabilities/">vulnerability</a>, this verification code was <a href="https://github.com/miyagawa/cpanminus/pull/638">removed</a>. Even though PowerShell is <a href="https://learn.microsoft.com/en-us/powershell/scripting/install/install-powershell?view=powershell-7.5">supported</a> on non-Windows platforms, Authenticode signature verification <a href="https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-authenticodesignature?view=powershell-7.5#notes">is</a> <a href="https://github.com/PowerShell/PSResourceGet/pull/1891">not</a><sup id="fnref:9"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:9">9</a></sup>. At one point, the PowerShell repository noted that this <a href="https://github.com/PowerShell/PowerShell/blob/b25b8df7cae323c376fe4770882ebbfd805fdbf4/docs/KNOWNISSUES.md#command-availability">issue</a> &ldquo;should be fixed in a future release.&rdquo;</p>
<h2 id="go-package-management-and-transparency-logs">Go package management and transparency logs</h2>
<p>Go’s built-in package manager is the only one I tested that verifies signatures by default, and it also introduces one final concept for cryptographic package integrity. When <code>go get</code> or <code>go mod download</code> fetches a package<sup id="fnref:10"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:10">10</a></sup>, it hashes the package contents and compares the hash, package name, and version against the <a href="https://go.dev/blog/module-mirror-launch">checksum database</a>. The contents of the database are registry-signed (analogous to PGP signatures in Perl&rsquo;s PAUSE server), and the default checksum database public key is <a href="https://github.com/golang/go/blob/master/src/cmd/go/internal/modfetch/key.go">hardcoded</a> in Go&rsquo;s source code. As long as the checksum database&rsquo;s private key is used honestly, this design ensures that the package name and version are enough to uniquely identify the binary contents of a package. As a result, the <code>go.mod</code> lockfile achieves package integrity without needing to store cryptographic hashes.<sup id="fnref:11"><a class="footnote-ref" href="https://blog.trailofbits.com/index.xml#fn:11">11</a></sup></p>
<p>Go&rsquo;s checksum database is an example of a transparency log, or an immutable, global, tamper-resistant log of metadata. The same capability is provided by Sigstore&rsquo;s <a href="https://docs.sigstore.dev/logging/overview/">Rekor</a> and certificate transparency logs. In package managers, it cryptographically ensures that the package manager only ever installs the same binaries recorded by the transparency log. If everyone agrees on the transparency log, then everyone agrees on the package contents. This makes it more difficult for an adversary to selectively and undetectably target a victim with a malicious package. Transparency logs can still fail if there are <a href="https://www.cve.org/CVERecord?id=CVE-2026-56865">other</a> <a href="https://www.cve.org/CVERecord?id=CVE-2026-56864">vulnerabilities</a>, the log&rsquo;s private key is compromised, or no one checks the transparency log for malicious behavior.</p>
<p>Of all the package managers I tested, Go performed the best at maintaining cryptographic integrity in the face of a compromised package repository or proxy. However, the registry-signature-like design means that much of the system&rsquo;s trust is concentrated in a single private key.</p>
<h2 id="a-proposed-cryptographic-design-for-package-managers">A proposed cryptographic design for package managers</h2>
<p>One potential approach that combines the ideas in this post is to include signature information in the lockfile. Rather than commit to the hash of a particular package, the lockfile could commit to a developer&rsquo;s identity or public key. This reuses much of the infrastructure in place for lockfile hashes, but it separates the question of immediate updates from the question of package integrity.</p>
<p>With this design, the lockfile could specify a single dependency version (for build reproducibility) or a lower bound (for immediate updates), and the included identity ensures that a malicious repository or proxy cannot easily tamper with whatever package version the manager resolves to. In addition, a transparency log can protect against selective targeting, building on Sigstore&rsquo;s identity-based signing and transparency log service. Sigstore avoids long-lived keys by default, but it also <a href="https://docs.sigstore.dev/cosign/key_management/overview/">supports</a> self-managed keys, KMS providers, and hardware tokens. This gives an easily adopted and secure default while still giving flexibility to developers who desire more control over their keys.</p>
<p>This idea is not new and not my own. Attestation identities are part of the <code>pylock.toml</code> Python lockfile <a href="https://packaging.python.org/en/latest/specifications/pylock-toml/#packages-attestation-identities">specification</a>, the <code>trusted-keys</code> in Gradle&rsquo;s <a href="https://docs.gradle.org/current/userguide/dependency_verification.html">verification metadata</a>, and the <code>pgp-keys-map.list</code> file in the <code>pgpverify-maven-plugin</code> for Maven. This is the direction that many package managers are already moving towards, as evidenced by the increasing adoption of Sigstore into publishing workflows, attention on supply-chain security, and bugfixes that specifically cite potential tampering by a malicious adversary. There is increasing recognition that this is a problem, and increasing appetite to fix it.</p>
<p>It won&rsquo;t be easy. There are many subtle nuances that have to be considered and addressed, signing verification code needs to be developed and audited, and developers need to adopt the resulting design. In many of the package managers I reviewed as part of this project, I found <a href="https://openssf.org/">communities</a> of <a href="https://rust-lang.zulipchat.com/#narrow/stream/417663-tbd-signing">people</a> who have been thinking about and pushing for cryptographic integrity and package signing for years. They know best what those package managers need, and they deserve the resources to make this a reality.</p>
<p>One of the greatest cryptographic success stories in the past decade has been the <a href="https://transparencyreport.google.com/https/overview?hl=en">nearly universal</a> adoption of HTTPS, driven in part by industry and community recognition of the security risks of unencrypted traffic, and the nonprofit <a href="https://letsencrypt.org/">Let&rsquo;s Encrypt</a> providing free and easy-to-use TLS certificates as a public good. Package signing is in a similar state now to where HTTPS was a decade ago: persistent adversaries are a huge concern, and cryptographic security is nearly nonexistent. Universal package signing is not here yet, but it is on the horizon. With the right attention and investment, we can make it a reality.</p>
