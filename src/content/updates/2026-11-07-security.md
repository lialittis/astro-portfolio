## Trail of Bits Blog
*Security research and insights from Trail of Bits*

### [After Binance, check what your signing systems can approve](https://blog.trailofbits.com/2026/11/06/after-binance-check-what-your-signing-systems-can-approve/) - November 06, 2026

<p>Binance’s <a href="https://www.coindesk.com/business/2026/10/30/binance-arranges-usd6-34-billion-to-cover-losses-from-record-crypto-hack">October 2026 security incident</a> raises an operational question for every organization holding user funds: Can your security controls recognize when a valid signature grants an attacker wallet authority? If an organization only monitors transfers and ownership changes, it may miss the shift in wallet authority until assets move.</p>
<p>Binance’s <a href="https://www.binance.com/en/support/announcement/detail/c5a8729a97ac486d963784d96c5642d7">initial update</a> about the incident suggested that a compromised DevOps laptop allowed an attacker to access a service container and submit unauthorized withdrawals. Its <a href="https://www.binance.com/en/support/announcement/detail/d3306d9dca5243548c813b605e1d1751">second update</a> reported additional breaches but no evidence that wallet private keys had leaked. In its <a href="https://www.binance.com/en/blog/community/3229153443759566763">November 3 report</a>, Binance described a broader attack involving social engineering, misuse of an internal AI tool, stolen credentials, and unauthorized access to its wallet-signing service. The attacker nevertheless obtained valid signatures, illustrating a major risk: a compromised server with permission to request signatures can misuse a protected key without extracting it.</p>
<p>The attacker used an <a href="https://eips.ethereum.org/EIPS/eip-7702">EIP-7702</a> delegation that allows a wallet to sign a standing instruction: “Use this code when my account is called.” Ethereum keeps that instruction in place until it is changed or cleared using the wallet’s key. That enabled <a href="https://www.trmlabs.com/resources/blog/north-korea-steals-usd-6-36-billion-from-binance-in-the-largest-hack-in-history">repeated transfers</a>, including funds deposited after the first theft, without further signatures from Binance. Other Binance wallets were drained through ordinary signed transfers.</p>
<p>Transaction execution and monitoring systems must keep pace with Ethereum. EIP-7702 places delegation authorizations outside ordinary calldata. Session keys, recovery paths, authorization modules, Safe modules, and <a href="https://eips.ethereum.org/EIPS/eip-4337">ERC-4337 UserOperations</a> all add execution paths that signing policies and monitors must understand. Systems that have not been updated can miss malicious authority changes and asset movements, leaving wallets exposed. Teams must update their detection rules and test that these attack paths are covered.</p>
<p>If you’re responsible for securing wallet infrastructure, start with our checklist.</p>
<h2 id="four-steps-to-strengthen-wallet-security">Four steps to strengthen wallet security</h2>
<p>These four recommendations address the risks exposed by the attack. We also provide tests to help you verify that these security controls work.</p>
<h3 id="1-reduce-access-to-signing-infrastructure">1. Reduce access to signing infrastructure</h3>
<p>Document every service and API that can request wallet signatures, who can call it, and what it can authorize, including transfers, delegation, and arbitrary data. Review this inventory whenever wallet functionality changes on supported chains. Separate signing infrastructure from everyday business systems and verify transaction details through an independent system. Use our <a href="https://blog.trailofbits.com/2025/02/28/threat-modeling-the-trail-of-bits-way/">TRAIL method</a> to trace how a compromised laptop or server could reach signing.</p>
<p><strong>Verify the result:</strong></p>
<ul>
<li>For each identified compromise path, use the access and credentials available to the compromised system to attempt an unapproved action. Identify the control expected to block it and retain evidence that no usable signature was produced.</li>
</ul>
<h3 id="2-treat-delegation-as-an-administrative-privilege">2. Treat delegation as an administrative privilege</h3>
<p>Configure signing services to recognize requests that change account authority. Reject <a href="https://eips.ethereum.org/EIPS/eip-7702">EIP-7702</a> authorizations for custody externally owned accounts (EOAs) that do not need delegation, and ensure generic digest-signing APIs cannot bypass that restriction. Where delegation is required, separately approve the authorizing account, delegate address and code, chain, and nonce. Before evaluating execution, simulations must apply the proposed delegation and inspect changes to permissions and future execution authority alongside immediate balance changes.</p>
<p><strong>Verify the result:</strong></p>
<ul>
<li>
<p>Delegation requests for accounts with delegation disabled are rejected through both dedicated and generic signing interfaces.</p>
</li>
<li>
<p>Changing an approved account, delegate, chain, or nonce requires renewed approval. Simulations expose added authority even when the transaction moves no assets immediately.</p>
</li>
</ul>
<h3 id="3-limit-damage-even-if-signing-is-compromised">3. Limit damage even if signing is compromised</h3>
<p>Even after delegation, the original EOA key can still transfer funds or change the delegate. This means that if the key is compromised, an attacker can bypass limits enforced by the delegate. Protect those assets with separate custody controls that the operational key cannot change. Our <a href="https://blog.trailofbits.com/2025/09/05/safer-cold-storage-on-ethereum/">cold-storage guidance</a> describes independently enforced limits, monitored delays on sensitive actions, and a separate configuration authority.</p>
<p><strong>Verify the result:</strong></p>
<ul>
<li>
<p>Treat the operational key as compromised and attempt direct transfers, delegate replacement, and policy changes. Confirm these paths cannot bypass the claimed protections, including shortening or removing delays.</p>
</li>
<li>
<p>Exercise incident response against a malicious withdrawal. Record alert and containment times, and demonstrate that responders can cancel or contain the withdrawal before execution. Confirm that the blocked withdrawal cannot subsequently execute.</p>
</li>
</ul>
<h3 id="4-detect-changes-in-wallet-authority">4. Detect changes in wallet authority</h3>
<p>Map each wallet to the assets and contracts it controls, including wallets that hold no funds. Alerts should identify the affected systems and privileges (e.g., an unapproved delegation on an account that can upgrade funded vaults). Attribute direct calls, module execution, and <a href="https://ercs.ethereum.org/ERCS/erc-4337">ERC-4337 operations</a> to their authorization paths.</p>
<p><strong>Verify the result:</strong></p>
<ul>
<li>
<p>Test various delegation scenarios, mixed authorization tuples, multisig-module execution, and failed UserOperations inside successful bundles.</p>
</li>
<li>
<p>Monitoring should reconstruct authority changes and asset movements in order, identify affected systems, and distinguish detection from controls that block execution before funds move.</p>
</li>
</ul>
<h2 id="make-signing-infrastructure-an-ongoing-responsibility">Make signing infrastructure an ongoing responsibility</h2>
<p>If your organization runs wallets or signing services, take another look at how they’re secured. Test whether your signing policies account for EIP-7702 and ERC-4337, whether independent safeguards still work if an attacker gains access to signing, and whether your monitoring catches changes to accounts and permissions.</p>
<p>Give someone ownership of this review and put it on a regular schedule. Run it again whenever you change the protocols you support, the wallets you use, or your signing services.</p>
